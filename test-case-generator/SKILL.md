# 测试用例生成器

## 概述

根据需求文档生成结构化测试用例（Markdown 格式），采用迭代式生成策略，分 3 轮批次逐步完善用例，确保高覆盖率和高质量。

**核心设计**：
- **Markdown 输出**：人类可读，结构清晰
- **迭代式生成**：分 3 轮批次生成（核心正向 → 反向边界 → 低优先级），每轮检查完备性
- **质量优先**：每轮生成后立即检查并修正，确保覆盖度和准确性

## 多角色协作

**测试分析师**：识别测试项、规划场景、评估优先级、理解业务规则
**用例设计师**：运用设计方法、编写步骤、确保可执行性、设计安全场景
**质量审查员**：检查完备性、检测重复、验证分布、审查质量

## 适用场景

当用户提供需求文档并需要：
- 生成结构化的测试用例文档
- 确保高覆盖率（场景完整、优先级合理）
- 避免冗余用例（重复性检查）

在当前工作目录创建 `需求名称/` 目录，包含以下文件：

```
需求名称/
├── test-items.md        # Step 1: 测试项清单
├── test-plan.md         # Step 2: 场景规划
├── test-cases.md        # Step 3: 测试用例（Markdown）
├── test-cases.xlsx      # Step 6: 测试用例（Excel）★ 强制
├── test-cases.xmind     # Step 6: 测试用例（XMind）★ 强制
├── coverage-report.md   # Step 5: 覆盖度报告
└── stats-report.md      # Step 5: 统计报告
```

## 执行流程

按顺序执行以下步骤：

```
Step 0: 背景信息收集
    ↓
Step 1: 测试项识别 ➡️ 输出 test-items.md
    ↓
Step 2: 场景规划 ➡️ 输出 test-plan.md
    ↓
Step 3: 分批次生成用例（3轮迭代）
    ├─ 对每个模块：
    │   Round 1: 核心正向（P1）➡️ 检查 ➡️ 修正
    │   Round 2: 反向边界（P2核心反向 + P4基本反向）➡️ 检查 ➡️ 去重
    │   Round 3: 低优先级（P3 + P5）➡️ 检查 ➡️ 去重
    └─ 模块审查（覆盖度 + 分布 + 质量）
    ↓
Step 4: 全局审查
    ↓
Step 5: 生成报告 ➡️ coverage-report.md + stats-report.md
    ↓
Step 6: 格式转换（强制）➡️ test-cases.xlsx + test-cases.xmind
```

### Step 0: 背景信息收集

**[输入]** 需求文档路径（用户提供）
**[输出]** 需求名称/ 目录 + 背景信息

**执行要求**：

1. **确认需求文档路径**
2. **推断项目类型**：从需求内容判断（Web应用/移动App/API服务/硬件系统/AI应用）
3. **识别关注重点**：从需求关键词判断（功能/安全/性能/兼容性/用户体验）
4. **确定特殊要求**：是否需要埋点测试、AI效果测试、硬件交互测试等

**创建输出目录**（强制）：
```python
from pathlib import Path
output_dir = Path.cwd() / requirement_name
output_dir.mkdir(exist_ok=True)
```

**输出格式**（示例）：
```markdown
# 背景信息

- **项目类型**：Web应用 - 企业管理系统
- **关注重点**：功能完整性、安全防护
- **特殊要求**：需包含埋点测试
```

### Step 1: 测试项识别

**[输入]** 需求文档
**[输出]** test-items.md

**执行要求**（按 6 个维度识别）：

1. **按模块识别**：根据需求文档的章节结构识别功能模块
2. **按操作识别**：每个用户可执行的操作 = 1 个测试项
3. **按 CRUD 识别**：每个数据实体的增删改查 = 各 1 个测试项
4. **按业务规则识别**：每个关键业务规则（如折扣计算、审批流程）= 1 个测试项
5. **按状态变化识别**：每个状态机（如订单状态）= 1 个测试项
6. **按集成点识别**：每个第三方服务集成（如支付、短信）= 1 个测试项

**业务价值评估**（强制）：
- **高**：核心业务流程（登录、支付、下单、数据保存）
- **中**：辅助功能（修改信息、查询记录、消息通知）
- **低**：边缘功能（高级设置、管理员报表、归档数据）

```markdown
# 测试项清单

## 模块：用户登录

| 测试项 | 业务价值 | 说明 |
|-------|---------|------|
| 用户登录流程 | 高 | 用户名密码登录 |
| 登录安全防护 | 高 | 防注入、防暴力破解 |
| 登录状态管理 | 中 | 记住密码、自动登录 |

## 模块：订单管理

| 测试项 | 业务价值 | 说明 |
|-------|---------|------|
| 订单创建 | 高 | 创建新订单 |
| 订单查询 | 中 | 查询历史订单 |
| 订单取消 | 中 | 取消未支付订单 |
| 订单状态流转 | 高 | 待支付→已支付→已发货→已完成 |
```

**关键原则**：
- 粒度适中：每个测试项预估生成 3-8 条用例
- 按模块分组组织
- 业务价值直接影响后续优先级判定

### Step 2: 场景规划

**[输入]** test-items.md（测试项清单）
**[输出]** test-plan.md（场景规划表）

**执行要求**：

为每个测试项规划场景覆盖，明确轮次、优先级、设计方法、预估用例数。

**场景类型映射**：

| 场景类型 | 定义 | 优先级 | 设计方法 | 生成轮次 |
|---------|------|-------|---------|---------|
| 正向场景 | 正常输入，预期成功 | P1/P2 | 场景法（基本流） | Round 1 |
| 反向场景 | 异常输入，预期失败 | P2/P4 | 等价类（无效） | Round 2 |
| 边界场景 | 边界值输入 | P2/P4 | 边界值分析 | Round 2 |
| 安全场景 | 攻击性输入 | P2 | 错误推测 | Round 2 |
| 性能场景 | 并发、大数据量 | P2/P4 | 性能测试 | Round 2/3 |
| 不常用场景 | 低频操作 | P3/P5 | 场景法（备选流） | Round 3 |

**规划约束**（强制）：
- 每个测试项必须规划场景
- 必须明确轮次、优先级、设计方法
- 必须预估用例数（3-8 个）
- 高业务价值测试项必须规划更全面的场景

**输出 test-plan.md**：

```markdown

|-----|---------|-------|---------|----------|------|
| Round 1 | 正常登录 | P1 | 场景法（基本流） | 2 | 普通用户、管理员登录 |

**覆盖目标**：
- [x] 正向场景（至少 1 个）
- [x] 核心反向（至少 2 个）
- [x] 边界值（连续错误次数）
- [x] 不常用场景（记住密码、自动登录）

|-----|---------|-------|---------|----------|------|

| Round 2 | XSS 防护 | P2 | 错误推测 | 1 | 脚本注入 |

**覆盖目标**：
- [x] SQL 注入防护

**预估总用例数**：4
```

**关键原则**：
- 每个测试项必须规划场景
- 明确轮次、优先级、设计方法
- 预估用例数（用于后续覆盖度检查）
- 高业务价值测试项场景更全面

### Step 3: 分批次生成用例（3轮迭代）

**关键策略**：分 3 轮批次生成，每轮生成后立即检查并修正，避免一次性生成导致覆盖不足或冗余。

---

#### Round 1: 核心正向用例（P1）

**[输入]** test-plan.md（核心测试项清单）
**[约束]** P1 only | 正向 only | 每个核心测试项 ≥1 用例
**[输出]** test-cases.md（追加写入）

**执行要求**：

1. **提取基本流**：从需求中识别每个核心测试项的正常路径
2. **识别核心路径**：登录、下单、支付等关键业务流程
3. **编写 P1 用例**：只生成正向场景，每个核心测试项至少 1 个
4. **设置前置条件**：明确测试环境和数据准备
5. **编写执行步骤**：具体可执行，避免模糊描述
6. **定义预期结果**：明确系统反应，可验证

**生成约束**（严格遵守）：
- 只能生成 P1 优先级用例，禁止生成其他优先级
- 只能生成正向场景，禁止带 `|反向` 标记
- 使用场景法（基本流）
- 每个核心测试项必须至少 1 个用例

**输出示例**（追加到 test-cases.md）：

```markdown
# 用户登录

## 正常登录

### 验证用户成功登录系统
P1|功能

[前置]
- 系统已部署
- 存在有效账号 test/123456

[步骤]
1. 打开登录页面 ➡️ 页面显示登录表单
2. 输入用户名 test
3. 输入密码 123456
4. 点击登录按钮 ➡️ 登录成功，跳转首页，右上角显示用户名
```

**[检查]** 生成后立即执行，未通过禁止继续：

**完备性检查**（必须逐项验证）：
- [ ] 核心测试项覆盖率 = 100% → 未达标立即补充
- [ ] 用例名称以"验证"开头 → 不符合立即修正
- [ ] 优先级全部 = P1 → 错误立即修正
- [ ] 无 `|反向` 标记 → 错误立即修正
- [ ] 步骤具体可执行 → 模糊描述立即改写
- [ ] 预期结果明确可验证 → 模糊词立即改写

**[修正]** 循环执行直到通过：

```
检查 → 发现问题 → 立即修正 → 重新检查 → 通过 → Round 2
       ↑___________________|
       未通过禁止继续，必须修正
```

**修正要求**（强制执行）：
- 遗漏测试项 → 禁止继续，立即补充，重新检查
- 格式错误 → 禁止继续，立即修正，重新检查
- 模糊描述 → 禁止继续，立即改写，重新检查

**通过标准**（必须全部满足）：
- 核心测试项覆盖率 = 100%
- 所有检查项通过
- 无格式错误、无模糊描述

#### Round 2: 反向和边界用例（P2核心反向 + P4基本反向）

**[输入]** Round 1 生成的 P1 用例 + test-plan.md
**[约束]** P2/P4 only | 反向场景 | 基于 Round 1 识别反向场景
**[输出]** test-cases.md（追加写入）

**执行要求**：

1. **基于 Round 1 识别反向场景**：每个正向输入 → 对应无效输入
2. **应用等价类划分**：区分有效/无效等价类，取代表值
3. **应用边界值分析**：测试上点、离点、内点（最大±1、最小±1）
4. **识别安全场景**：SQL注入、XSS、CSRF、越权等
5. **生成 P2（核心反向）**：核心功能的异常处理
6. **生成 P4（基本反向）**：基本功能的异常处理

**生成约束**（严格遵守）：
- 只能生成 P2（核心反向）或 P4（基本反向）
- 禁止生成 P1、P3、P5
- 反向用例必须标记 `|反向`
- 使用等价类（无效类）+ 边界值分析 + 错误推测法

**输出示例**（追加到 test-cases.md）：

```markdown
## 异常登录

### 验证密码错误时登录失败
P2|功能|反向

[前置]存在有效账号 test

[步骤]
1. 打开登录页面
2. 输入用户名 test 和错误密码 wrongpass
3. 点击登录按钮 ➡️ 提示"用户名或密码错误"，登录框保持显示

---

## 安全验证

### 验证系统拦截 SQL 注入攻击
P2|安全性|反向

[步骤]
1. 在用户名输入 ' OR '1'='1
2. 点击登录按钮 ➡️ 登录失败，提示输入错误
3. 检查数据库日志 ➡️ SQL 被转义，无异常查询记录

[备注]确保使用参数化查询或 ORM
```

**[检查]** 生成后立即执行，未通过禁止继续：

**完备性检查**（必须逐项验证）：
- [ ] 核心测试项反向场景覆盖 = 100% → 未达标立即补充
- [ ] 边界值已覆盖（上点/离点/内点）→ 缺失立即补充
- [ ] 安全场景已覆盖（SQL注入/XSS）→ 缺失立即补充
- [ ] 反向用例带 `|反向` 标记 → 遗漏立即补充
- [ ] 预期结果明确错误提示 → 模糊立即改写

**重复性检查**（必须执行）：
- 步骤完全相同 → 立即去重
- 用例名称相似度 > 0.8 → 确认后去重

**[修正]** 循环执行直到通过：

```
检查 → 发现问题 → 立即修正 → 重新检查 → 通过 → Round 3
       ↑___________________|
       未通过禁止继续，必须修正
```

**修正要求**（强制执行）：
- 遗漏反向场景 → 禁止继续，立即补充，重新检查
- 重复用例 → 禁止继续，立即去重，重新检查
- 边界值未覆盖 → 禁止继续，立即补充，重新检查
- 安全场景缺失 → 禁止继续，立即补充，重新检查

**通过标准**（必须全部满足）：
- 核心测试项反向场景覆盖率 = 100%
- 无重复用例
- 安全场景已覆盖
- 所有检查项通过

#### Round 3: 低优先级用例（P3 + P5）

**[输入]** Round 1+2 生成的用例 + test-plan.md + 优先级分布统计
**[约束]** P3/P5 | 不常用场景 | 平衡优先级分布
**[输出]** test-cases.md（追加写入）

**执行要求**：

1. **识别不常用场景**：用户偶尔才用的功能（P3）
2. **识别边缘功能**：极少使用的功能（P5）
3. **补充 P4 用例**：如 Round 2 后 P4 过少，补充基本功能反向用例
4. **平衡优先级分布**：确保分布符合目标（P1 10-15%, P2 35-40%, P3 15-20%, P4 20-25%, P5 5-10%）
5. **场景法（备选流）**：生成低频场景用例

**生成约束**（严格遵守）：
- 只能生成 P3（基本功能不常用）或 P5（极少使用）
- 禁止生成 P1、P2
- 如需平衡分布，可补充 P4
- 使用场景法（备选流）

**输出示例**（追加到 test-cases.md）：

```markdown
## 登录辅助功能

### 验证记住密码功能正常
P3|功能

4. 退出登录
5. 重新打开登录页 ➡️ 用户名密码自动填充
```

**[检查]** 生成后立即执行，未通过禁止继续：

**模块最终覆盖度检查**（必须逐项验证）：
- [ ] 所有测试项场景覆盖完整
- [ ] 优先级分布在允许范围内（P1:10-15%, P2:35-40%, P3:15-20%, P4:20-25%, P5:5-10%）
- [ ] 无重复用例
- [ ] 无质量问题

**[修正]** 循环执行直到通过：

```
检查 → 发现问题 → 立即修正 → 重新检查 → 通过 → 下一模块
       ↑___________________|
       未通过禁止继续，必须修正
```

**修正要求**（强制执行）：
- 优先级分布不合理 → 禁止继续，调整或补充，重新检查
- 场景缺失 → 禁止继续，立即补充，重新检查
- 重复用例 → 禁止继续，立即去重，重新检查
- 质量问题 → 禁止继续，立即修正，重新检查

**通过标准**（必须全部满足）：
- 所有测试项场景覆盖完整
- 优先级分布在允许范围内（见上表）
- 无重复用例
- 无质量问题

**[循环]** 重复 Round 1-3 流程，直到所有模块处理完毕。

### Step 4: 全局审查

**[输入]** 所有模块的 test-cases.md
**[约束]** 全局视角 | 跨模块检查
**[输出]** 修正后的 test-cases.md

**[执行]** 运行验证脚本：


脚本输出 stats-report.md，包含：
- 总用例数、模块数
- 优先级分布
- 测试类型分布
- 正向/反向分布
- 验证问题列表

**[检查]** 全局质量检查（必须逐项验证）：

**格式一致性**（强制）：
- [ ] 所有用例名称以"验证"开头 → 不符合立即修正
- [ ] 元数据格式 `P1|功能|反向` → 错误立即修正
- [ ] 优先级在 P1-P5 范围内 → 错误立即修正
- [ ] 测试类型为有效值 → 错误立即修正
- [ ] 步骤使用 `➡️` 分隔符 → 错误立即修正

**内容质量**（强制）：
- [ ] 步骤具体可执行 → 模糊词立即改写（禁止：正确操作、按要求输入）
- [ ] 预期结果明确可验证 → 模糊词立即改写（禁止：显示正常、操作成功）
- [ ] 前置条件明确具体 → 模糊立即改写
- [ ] 反向用例标记 `|反向` → 遗漏立即补充

**覆盖完整性**（强制）：
- [ ] 每个测试项至少 1 个正向场景 → 缺失立即补充
- [ ] 核心测试项至少 1 个反向场景 → 缺失立即补充
- [ ] 安全测试项有安全场景 → 缺失立即补充
- [ ] 边界值输入已覆盖 → 缺失立即补充

**优先级分布检查**（强制）：
- P1: 10-15%（允许 8-18%）
- P2: 35-40%（允许 30-45%）
- P3: 15-20%（允许 10-25%）
- P4: 20-25%（允许 15-30%）
- P5: 5-10%（允许 0-15%）
- 超出范围 → 调整优先级或补充用例

**重复性检查**（强制）：
- 跨模块检测重复用例 → 发现立即去重

**[修正]** 循环执行直到通过：

```
检查 → 发现问题 → 立即修正 → 重新检查 → 通过 → Step 5
       ↑___________________|
       未通过禁止继续，必须修正
```

**修正要求**（强制执行）：
- 格式问题 → 禁止继续，立即修正，重新检查
- 质量问题 → 禁止继续，立即改写，重新检查
- 覆盖缺失 → 禁止继续，返回 Step 3 补充，重新检查
- 分布不合理 → 禁止继续，调整优先级或补充用例，重新检查

**通过标准**（必须全部满足）：
- 所有检查项通过
- 优先级分布在允许范围内
- 无重复用例
- 无质量问题

### Step 5: 生成报告

**[输入]** 最终的 test-cases.md + test-items.md
**[输出]** coverage-report.md + stats-report.md

**执行要求**：

## 测试用例格式规范

### 层级结构

```markdown
# 一级分组（模块）
## 二级分组（场景/功能点）
### 用例名称
```

### 用例结构

```markdown
### 验证用户成功登录系统
P1|功能

[前置]
- 系统已部署
- 存在有效账号 test/123456

[步骤]
1. 打开登录页面 ➡️ 页面显示登录表单
2. 输入用户名 test
3. 输入密码 123456
4. 点击登录按钮 ➡️ 登录成功，跳转首页

[备注]核心冒烟用例
```

### 字段说明

| 字段 | 格式 | 必填 | 说明 |
|------|------|------|------|
| 用例名称 | `### 验证xxx` | 是 | 以"验证"开头，主谓宾结构 |
| 元数据 | `P1|功能|反向` | 是 | 优先级\|测试类型\|反向标记 |
| 前置条件 | `[前置]` | 否 | 测试执行前必须满足的条件 |
| 测试步骤 | `[步骤]` | 是 | `n. 操作` 或 `n. 操作 ➡️ 预期结果` |
| 备注 | `[备注]` | 否 | 补充说明 |

**详细规范参见**：`references/test-case-format.md`

## 优先级定义（固定规则）

| 优先级 | 定义 | 判断规则 |
|-------|------|---------|
| P1 | 核心功能正向测试 | 核心业务 + 正向场景 |
| P2 | 基本功能（常用场景） + 核心功能反向测试 | 基本功能正向 OR (核心业务 + 反向场景) |
| P3 | 基本功能（不常用场景） | 基本功能 + 低频场景 |
| P4 | 基本功能反向测试 | 基本功能 + 反向场景 |
| P5 | 不常用功能测试 | 低频功能 |

**判断流程**：

```
是核心业务流程？（登录、支付、下单等）
├─ 是 ➡️ 正向场景？ ➡️ P1 / 反向场景？ ➡️ P2
└─ 否
   ├─ 是基本功能？（修改信息、查询等）
   │  ├─ 是常用场景？ ➡️ P2
   │  ├─ 是不常用场景？ ➡️ P3
   │  └─ 是反向场景？ ➡️ P4
   └─ 不常用功能？（高级设置、管理员报表）➡️ P5
```

**典型示例**：

| 场景 | 优先级 | 原因 |
|------|-------|------|
| 用户成功登录 | P1 | 核心 + 正向 |
| 密码错误登录失败 | P2 | 核心 + 反向 |
| 修改个人昵称成功 | P2 | 基本 + 常用 |
| 修改密码成功 | P3 | 基本 + 不常用 |
| 上传头像格式错误 | P4 | 基本 + 反向 |
| 管理员导出报表 | P5 | 不常用 |

**详细说明参见**：`references/priority-guide.md`

## 测试类型

| 测试类型 | 核心目标 | 适用场景 |
|---------|---------|---------|
| 功能 | 验证功能正确性 | 业务逻辑、数据处理、流程完整性 |
| 兼容性 | 验证跨环境运行 | 多浏览器、多设备、多分辨率 |
| 易用性 | 验证用户体验 | 界面布局、操作流程、提示信息 |
| 性能 | 验证性能指标 | 响应时间、并发量、资源占用 |
| 稳定性 | 验证长期运行 | 7x24小时运行、内存泄漏 |
| 安全性 | 验证安全防护 | 认证授权、注入防护、越权访问 |
| 可靠性 | 验证故障恢复 | 断网恢复、服务降级、数据一致性 |

**扩展类型**（按需使用）：效果（AI类）、效果（硬件类）、可维护性、可移植性、埋点、集成

**选择规则**：

```
涉及安全防护？ ➡️ 安全性
涉及性能指标？ ➡️ 性能
涉及多模块协作？ ➡️ 集成（归入功能）
涉及跨环境运行？ ➡️ 兼容性
涉及故障恢复？ ➡️ 可靠性
涉及用户体验？ ➡️ 易用性
涉及长期运行？ ➡️ 稳定性
默认 ➡️ 功能
```

**详细说明参见**：`references/test-type-guide.md`

## 反向用例判断

**按输入类型判断**：

| 输入类型 | 是否反向 | 示例 |
|---------|---------|------|
| 正常/有效输入 | 否 | 正确用户名密码 |
| 异常/无效输入 | 是 | 错误密码、不存在的用户 |
| 边界值输入 | 是 | 密码长度为1或128 |
| 攻击性输入 | 是 | SQL注入、XSS脚本 |
| 空值/缺失输入 | 是 | 不填用户名提交 |

## 注意事项

1. **迭代式生成，不要一次性生成所有用例** - 分 3 轮批次，每轮检查
2. **每轮生成后立即检查** - 完备性、重复性、优先级分布
3. **用例名称以"验证"开头** - 主谓宾格式
4. **优先级是固定规则** - P2 包含基本功能常用 + 核心功能反向
5. **反向用例按输入类型判断** - 异常/攻击性/空值输入 = 反向
6. **正向用例省略 `[反向]` 标记**
7. **预期结果非必填** - 中间步骤可省略
8. **禁止模糊描述** - 避免"正常"、"成功"、"正确"等模糊词
