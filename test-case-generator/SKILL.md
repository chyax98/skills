# 测试用例生成器

根据需求文档生成结构化测试用例，分 3 轮迭代，每轮检查修正，输出 MD/Excel/XMind。

**最终输出**（7个文件）：
```
需求名称/
├── test-items.md        # 测试项清单
├── test-plan.md         # 场景规划
├── test-cases.md        # 测试用例（Markdown）
├── test-cases.xlsx      # 测试用例（Excel）
├── test-cases.xmind     # 测试用例（XMind）
├── coverage-report.md   # 覆盖度报告
└── stats-report.md      # 统计报告
```

---

## 工作流程

### 🎯 阶段 1: 测试项识别

**执行**：
1. 读取需求文档
2. 按 6 个维度识别测试项（模块、操作、CRUD、业务规则、状态变化、集成点）
3. 评估业务价值（高/中/低）

**输出示例** (test-items.md)：
```markdown
## 模块：用户登录

| 测试项 | 业务价值 | 说明 |
|-------|---------|------|
| 用户登录流程 | 高 | 用户名密码登录 |
| 登录安全防护 | 高 | 防注入、防暴力破解 |
```

---

### 📋 阶段 2: 场景规划

为每个测试项规划场景覆盖，明确轮次和优先级。

**场景类型映射**：

| 场景 | 优先级 | 设计方法 | 轮次 |
|-----|-------|---------|-----|
| 正向场景 | P1/P2 | 场景法 | Round 1 |
| 反向场景 | P2/P4 | 等价类/边界值 | Round 2 |
| 安全场景 | P2 | 错误推测 | Round 2 |
| 不常用场景 | P3/P5 | 场景法 | Round 3 |

**输出示例** (test-plan.md)：
```markdown
### 测试项：用户登录流程

| 轮次 | 场景 | 优先级 | 预估数 |
|-----|------|-------|--------|
| Round 1 | 正常登录 | P1 | 2 |
| Round 2 | 密码错误 | P2 | 2 |
| Round 2 | SQL注入 | P2 | 1 |
| Round 3 | 记住密码 | P3 | 1 |
```

---

### 🔄 阶段 3: 用例生成（3轮迭代）

**CRITICAL**: 分 3 轮批次生成，每轮立即检查修正，禁止一次性生成所有用例。

#### Round 1: 核心正向（P1）

**约束**：
- 只生成 P1 优先级
- 只生成正向场景（无 `|反向`）
- 每个核心测试项至少 1 个用例

**输出示例**：
```markdown
### 验证用户成功登录系统
P1|功能

[前置]
- 系统已部署
- 存在有效账号 test/123456

[步骤]
1. 打开登录页面 ➡️ 页面显示登录表单
2. 输入用户名 test
3. 输入密码 123456
4. 点击登录按钮 ➡️ 登录成功，跳转首页
```

**验证检查**（必须逐项验证）：
- [ ] 核心测试项覆盖率 = 100% → 未达标立即补充
- [ ] 用例名称以"验证"开头 → 不符合立即修正
- [ ] 优先级全部 = P1 → 错误立即修正
- [ ] 无 `|反向` 标记 → 错误立即修正
- [ ] 步骤具体可执行 → 模糊描述立即改写
- [ ] 预期结果明确可验证 → 模糊词立即改写

未通过禁止进入 Round 2，必须修正后重新检查。

---

#### Round 2: 反向边界（P2/P4）

**约束**：
- 基于 Round 1 识别反向场景
- 生成 P2（核心反向）+ P4（基本反向）
- 反向用例必须标记 `|反向`

**验证检查**（必须逐项验证）：
- [ ] 核心测试项反向覆盖 = 100% → 未达标立即补充
- [ ] 边界值已覆盖（上点/离点/内点）→ 缺失立即补充
- [ ] 安全场景已覆盖（SQL注入/XSS）→ 缺失立即补充
- [ ] 反向用例标记 `|反向` → 遗漏立即补充
- [ ] 预期结果明确错误提示 → 模糊立即改写
- [ ] 无重复用例 → 发现立即去重

未通过禁止进入 Round 3，必须修正后重新检查。

---

#### Round 3: 低优先级（P3/P5）

**约束**：
- 生成 P3（不常用）+ P5（极少使用）
- 平衡优先级分布

**验证检查**（必须逐项验证）：
- [ ] 所有测试项场景覆盖完整 → 缺失立即补充
- [ ] 优先级分布在允许范围内 → 不合理立即调整
  - P1: 10-15%（允许 8-18%）
  - P2: 35-40%（允许 30-45%）
  - P3: 15-20%（允许 10-25%）
  - P4: 20-25%（允许 15-30%）
  - P5: 5-10%（允许 0-15%）
- [ ] 无重复用例 → 发现立即去重
- [ ] 无质量问题 → 发现立即修正

未通过禁止进入下一模块，必须修正后重新检查。

**循环**：重复 Round 1-3 流程，处理所有模块。

---

### ✅ 阶段 4: 全局审查

运行验证脚本：
```bash
uv run scripts/validate_md.py test-cases.md
```

**验证检查清单**（必须逐项验证）：

**格式一致性**：
- [ ] 所有用例名称以"验证"开头 → 不符合立即修正
- [ ] 元数据格式 `P1|功能|反向` → 错误立即修正
- [ ] 优先级在 P1-P5 范围内 → 错误立即修正
- [ ] 测试类型为有效值 → 错误立即修正
- [ ] 步骤使用 `➡️` 分隔符 → 错误立即修正

**内容质量**：
- [ ] 步骤具体可执行 → 模糊词立即改写（禁止：正确操作、按要求输入）
- [ ] 预期结果明确可验证 → 模糊词立即改写（禁止：显示正常、操作成功）
- [ ] 前置条件明确具体 → 模糊立即改写
- [ ] 反向用例标记 `|反向` → 遗漏立即补充

**覆盖完整性**：
- [ ] 每个测试项至少 1 个正向场景 → 缺失立即补充
- [ ] 核心测试项至少 1 个反向场景 → 缺失立即补充
- [ ] 安全测试项有安全场景 → 缺失立即补充
- [ ] 边界值输入已覆盖 → 缺失立即补充

**优先级分布**：
- [ ] P1: 10-15%（允许 8-18%）
- [ ] P2: 35-40%（允许 30-45%）
- [ ] P3: 15-20%（允许 10-25%）
- [ ] P4: 20-25%（允许 15-30%）
- [ ] P5: 5-10%（允许 0-15%）
- [ ] 超出范围 → 调整优先级或补充用例

**重复性检查**：
- [ ] 跨模块检测重复用例 → 发现立即去重

发现问题立即修正，重新检查，循环直到通过。

---

### 📊 阶段 5: 生成报告

生成 coverage-report.md 和 stats-report.md

**成功标准**：
- 测试项覆盖率 = 100%
- 优先级分布合理
- 反向用例占比 ≥ 15%
- 无格式错误、无模糊描述

---

### 🔄 阶段 6: 格式转换

**MANDATORY**: 必须转换为 Excel 和 XMind

```bash
uv run scripts/convert_to_excel.py test-cases.md -o test-cases.xlsx
uv run scripts/convert_to_xmind.py test-cases.md -o test-cases.xmind
```

验证：
- [ ] xlsx 和 xmind 生成成功
- [ ] 用例数量一致
- [ ] 格式转换无遗漏

## 测试用例格式

```markdown
### 验证用户成功登录系统
P1|功能

[前置]
- 系统已部署
- 存在有效账号 test/123456

[步骤]
1. 打开登录页面 ➡️ 页面显示登录表单
2. 输入用户名 test
3. 输入密码 123456
4. 点击登录按钮 ➡️ 登录成功，跳转首页
```

**格式规则**：
- 用例名称：`### 验证xxx`
- 元数据：`P1|功能|反向`
- 段落：`[前置][步骤][备注]`
- 分隔：`操作 ➡️ 预期结果`

详细规范：`references/test-case-format.md`

---

## 优先级定义

| 优先级 | 定义 |
|-------|------|
| P1 | 核心功能正向 |
| P2 | 基本功能常用 + 核心功能反向 |
| P3 | 基本功能不常用 |
| P4 | 基本功能反向 |
| P5 | 不常用功能 |

**判断流程**：
```
是核心业务？
├─ 是 → 正向？→ P1 / 反向？→ P2
└─ 否 → 常用？→ P2 / 不常用？→ P3 / 反向？→ P4
```

详细说明：`references/priority-guide.md`

## 测试类型

**基础**：功能、兼容性、易用性、性能、稳定性、安全性、可靠性
**扩展**：效果（AI类）、效果（硬件类）、可维护性、可移植性、埋点、集成

详细说明：`references/test-type-guide.md`

---

## 关键原则

**迭代生成**：
- 分 3 轮批次，每轮检查修正
- 禁止一次性生成所有用例

**质量控制**：
- 用例名称以"验证"开头
- 禁止模糊描述（正常、成功、按要求等）
- 反向用例标记 `|反向`

**强制输出**：
- Markdown + Excel + XMind（三种格式必须全部输出）
