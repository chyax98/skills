# 测试用例设计方法指南

**版本**: v1.0
**日期**: 2025-12-17

---

## 1. 设计核心思想

测试用例设计的核心在于**以最小的测试工作量获得最大的覆盖率**。

设计思路遵循从"点"到"线"再到"面"的逻辑：

```
数据维度（点）→ 逻辑维度（线）→ 业务维度（面）
```

---

## 2. 设计方法

### 2.1 数据维度：针对输入数据

#### 等价类划分法

将输入数据分为"有效"和"无效"两类。如果一个输入在某个范围内是等效的，测其中一个即可代表全部。

**思路**：减少穷举，用少量代表性数据覆盖大范围

**示例**：年龄输入框（有效范围 1-120）

| 等价类 | 取值范围 | 代表值 | 预期结果 |
|-------|---------|-------|---------|
| 有效等价类 | 1-120 | 25 | 输入成功 |
| 无效等价类（过小） | <1 | 0, -1 | 提示错误 |
| 无效等价类（过大） | >120 | 121, 999 | 提示错误 |
| 无效等价类（非数字） | 非数字 | "abc", "中文" | 提示错误 |

#### 边界值分析法

是对等价类的补充。经验表明，错误往往发生在边界上。

**思路**：重点测试"刚好大于"、"刚好小于"和"等于"边界的值

**示例**：年龄输入框（有效范围 1-120）

| 边界点 | 测试值 | 说明 |
|-------|-------|------|
| 最小值-1 | 0 | 刚好小于下界（无效） |
| 最小值 | 1 | 下界（有效） |
| 最小值+1 | 2 | 刚好大于下界（有效） |
| 最大值-1 | 119 | 刚好小于上界（有效） |
| 最大值 | 120 | 上界（有效） |
| 最大值+1 | 121 | 刚好大于上界（无效） |

---

### 2.2 逻辑维度：针对复杂业务规则

#### 判定表驱动法

当功能逻辑涉及多个条件的组合时使用。

**思路**：列出所有条件和动作，分析所有可能的真假组合，确保逻辑无遗漏

**示例**：订单折扣规则
- 条件1：会员等级 >= 金卡
- 条件2：订单金额 >= 500
- 条件3：商品参与活动

| 规则 | 金卡会员 | 金额≥500 | 参与活动 | 折扣结果 |
|------|---------|---------|---------|---------|
| 1 | 是 | 是 | 是 | 8折 |
| 2 | 是 | 是 | 否 | 9折 |
| 3 | 是 | 否 | 是 | 9折 |
| 4 | 是 | 否 | 否 | 95折 |
| 5 | 否 | 是 | 是 | 9折 |
| 6 | 否 | 是 | 否 | 95折 |
| 7 | 否 | 否 | 是 | 95折 |
| 8 | 否 | 否 | 否 | 无折扣 |

#### 因果图法

用于分析输入与输出之间的依赖关系及约束条件。

**关系类型**：
- 恒等：输入A存在则输出B存在
- 非：输入A存在则输出B不存在
- 或：输入A或B存在则输出C存在
- 与：输入A和B都存在则输出C存在

**约束条件**：
- 互斥：多个输入不能同时为真
- 包含：至少一个输入必须为真
- 唯一：有且仅有一个输入为真

### 2.3 业务维度：针对业务流程

#### 场景法

模拟用户操作的完整流程。

**思路**：分为**基本流**和**备选流**，通过覆盖各种路径来测试系统整体功能

| 流程类型 | 定义 | 示例 |
|---------|------|------|
| 基本流 | 一切顺利的主流程 | 用户正常登录 → 浏览商品 → 加入购物车 → 下单 → 支付成功 |
| 备选流 | 出现错误、异常或分支的流程 | 密码错误、库存不足、支付失败、取消订单 |

**场景设计步骤**：
1. 识别基本流（正常路径）
2. 识别备选流（异常/分支路径）
3. 组合流程生成场景
4. 为每个场景设计用例

---

## 3. 综合运用策略

```
Step 1: 用场景法搞定主流程和主要分支
    ↓
Step 2: 用等价类/边界值填充具体输入数据
    ↓
Step 3: 遇到复杂逻辑判断，用判定表拆解
```

**实践建议**：

| 场景 | 推荐方法 |
|------|---------|
| 简单输入校验 | 等价类 + 边界值 |
| 表单多字段校验 | 等价类 + 边界值 + 组合 |
| 复杂业务规则 | 判定表 |
| 完整业务流程 | 场景法 |
| 状态变化流程 | 状态迁移图 |

## 4. 设计原则

### 4.1 六大核心原则

| 原则 | 说明 |
|------|------|
| 覆盖原则 | 必须覆盖所有功能点、业务规则和非功能需求 |
| 独立原则 | 每个用例应尽量独立，不依赖其他用例的执行结果 |
| 明确原则 | 输入数据、操作步骤、预期结果必须清晰、无歧义 |
| 可复用原则 | 设计时考虑通用性，便于回归测试 |
| 简洁原则 | 语言简练，步骤不冗余 |
| 可行原则 | 用例必须可执行，前置条件和数据环境需可控 |

### 4.2 结构规范

| 要素 | 要求 |
|------|------|
| 前置条件 | 明确执行该用例所需的初始状态 |
| 测试步骤 | 分步骤描述操作，需具体明确 |
| 预期结果 | 必须明确具体的系统反应，不能模棱两可 |

**预期结果反例**：
- ❌ "系统正常"
- ❌ "显示成功"
- ❌ "功能正确"

**预期结果正例**：
- ✅ "弹出提示框，显示'保存成功'"
- ✅ "页面跳转到订单详情页，显示订单号 xxx"
- ✅ "数据库 user 表 status 字段更新为 1"

## 5. 质量检查清单

### 5.1 完整性检查

- [ ] 是否覆盖了所有需求文档中的功能点？
- [ ] 是否覆盖了主要业务流程（正常路径 + 异常路径）？
- [ ] 是否考虑了关联系统的交互？
- [ ] 是否包含了非功能性测试（性能、兼容性、安全性）？

### 5.2 规范性与清晰度检查

- [ ] 标题是否简洁明了，能概括测试目的？
- [ ] 前置条件是否准确？是否漏写了必要的数据准备？
- [ ] 步骤是否条理清晰？是否有冗余步骤？
- [ ] 预期结果是否唯一且明确？是否包含多维度验证？

### 5.3 逻辑与正确性检查

- [ ] 用例的逻辑是否符合业务规则？
- [ ] 边界值取值是否正确（上点、离点、内点）？
- [ ] 等价类划分是否合理（有效/无效）？
- [ ] 是否存在重复或冗余的用例？

### 5.4 可维护性与通用性

- [ ] 用例是否具有可重用性（适合回归测试）？
- [ ] 用例分级（优先级）是否合理？
- [ ] 是否易于第三方人员理解和执行？

## 6. 方法选择速查表

| 测试目标 | 推荐方法 | 适用场景 |
|---------|---------|---------|
| 输入字段校验 | 等价类 + 边界值 | 表单输入、参数校验 |
| 多条件组合 | 判定表 | 折扣规则、权限判断 |
| 状态变化 | 状态迁移图 | 订单状态、审批流程 |
| 业务流程 | 场景法 | 完整业务链路 |
| 异常处理 | 错误推测法 | 网络异常、数据异常 |
| 用户体验 | 探索性测试 | UI交互、易用性 |

---

## 总结

优秀的测试用例设计不仅仅是"找Bug"，更是对需求的深度分析。

- **思路**上要"全"（场景覆盖）且"准"（边界/逻辑覆盖）
- **规范**上要"清"（步骤清晰）且"实"（预期结果具体）
- **检查**上要"严"（通过 Checklist 确保没有遗漏和歧义）
