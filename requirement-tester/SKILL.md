# Requirement Tester - 需求测试分析器

系统性分析需求文档，识别问题点，补充异常场景，与用户交互确认，输出完整的需求问题清单。

## 设计理念

```
需求文档 → 问题识别 → 异常补充 → 交互确认 → 问题清单
```

**核心原则**:
- **缺陷分类驱动**: 基于 IEEE 1044 缺陷分类体系，系统性识别遗漏、歧义、不一致等问题
- **异常场景补充**: 自动识别需求中缺失的负向场景、边界条件、错误处理
- **交互式确认**: 与用户逐个确认问题，获取产品侧的明确答复
- **可追溯输出**: 生成结构化问题清单，支持后续跟踪和测试用例设计

## 适用场景

当用户提供需求文档（PRD/SRS/用户故事）并需要：
- 识别需求中的质量问题（遗漏、歧义、矛盾等）
- 补充产品未考虑的异常场景和边界条件
- 与产品/业务方交互确认需求细节
- 生成需求评审的问题清单
- 为测试用例设计建立完整基础

## 输入方式

支持以下输入：
1. **本地文件路径**: `/path/to/prd.md`, `/path/to/requirement.docx`
2. **URL**: `https://docs.example.com/prd`
3. **直接粘贴**: 用户直接粘贴需求文本

## 输出结构

```
{需求名称}/
├── issues.md                 # 问题清单（主文件）
├── exception-scenarios.md    # 补充的异常场景
└── summary.md                # 分析总结报告
```

## 多角色协作框架

### 需求分析师 (Requirement Analyst)
- 解析需求文档结构
- 拆解功能点和业务规则
- 识别需求间的依赖关系

### 缺陷侦探 (Defect Detective)
- 基于缺陷分类体系扫描问题
- 识别遗漏、歧义、不一致、不完整、不正确
- 评估问题严重程度

### 异常猎手 (Exception Hunter)
- 识别缺失的负向场景
- 补充边界条件和错误处理
- 分析并发、权限、数据异常

### 交互协调员 (Interaction Coordinator)
- 组织问题，分批与用户确认
- 记录用户回复和决策
- 更新问题状态

## 工作流程

### Phase 0: 文档获取与解析

**输入处理**:
```yaml
文件类型处理:
  markdown: 直接 Read 读取
  docx/pdf: 使用 document-skills 解析
  url: 使用 WebFetch 或 mcp__fetch__fetch 获取
  text: 直接使用用户粘贴内容
```

**信息收集**:
```markdown
请提供需求文档，支持以下方式：
1. 文件路径（如：/path/to/prd.md）
2. URL 地址
3. 直接粘贴需求内容

可选信息：
- 需求名称（用于生成目录）
- 分析深度：基础/标准/深度
- 重点关注：安全/性能/兼容性等
```

### Phase 1: 需求拆解

**需求分析师**执行：

#### 步骤 1.1: 功能点识别

将需求拆解为独立的功能点：

```markdown
功能点提取规则：
1. 每个用户可执行的操作为一个功能点
2. 每个系统自动触发的行为为一个功能点
3. 每个数据实体的 CRUD 操作分别为功能点
4. 每个业务规则为一个功能点
```

**输出格式**:

| ID | 模块 | 功能点 | 类型 | 描述 |
|----|------|-------|------|------|
| F001 | 用户管理 | 用户注册 | 用户操作 | 新用户填写信息完成注册 |
| F002 | 用户管理 | 手机号验证 | 系统行为 | 发送验证码并校验 |

#### 步骤 1.2: 业务规则提取

```markdown
业务规则提取：
- 数据校验规则（格式、范围、唯一性）
- 状态流转规则（状态机）
- 计算规则（公式、逻辑）
- 权限规则（谁能做什么）
- 时效规则（有效期、超时）
```

### Phase 2: 问题识别

**缺陷侦探**执行：

#### 步骤 2.1: 五类缺陷扫描

对每个功能点，检查以下缺陷类型（详见 `references/defect-taxonomy.md`）：

```yaml
遗漏检查 (Omission):
  - 功能描述是否完整？
  - 输入/输出是否都有说明？
  - 异常处理是否有定义？
  - 性能要求是否明确？
  - 安全要求是否说明？

歧义检查 (Ambiguity):
  - 是否有模糊词汇？（快速、大量、适当、尽量）
  - 条件判断是否明确？
  - 数值范围是否清晰？
  - 优先级是否定义？

不一致检查 (Inconsistency):
  - 同一术语定义是否一致？
  - 同一数据在不同场景定义是否一致？
  - 与其他系统接口定义是否一致？
  - 新需求与现有功能是否冲突？

不完整检查 (Incompleteness):
  - 流程是否有断点？
  - 状态是否有遗漏？
  - 角色权限是否完整？
  - 数据字段是否齐全？

不正确检查 (Incorrect):
  - 业务规则是否正确？
  - 计算公式是否正确？
  - 技术约束是否可行？
```

#### 步骤 2.2: 问题记录

**问题记录格式**:

```markdown
### R-001 [严重] 验证码发送失败处理

| 属性 | 值 |
|------|---|
| 功能点 | F002 手机号验证 |
| 类型 | 遗漏 |
| 位置 | 2.1.2 注册流程 |

**原始需求**: 系统向用户手机发送验证码

**问题**: 未说明验证码发送失败的处理方式

**建议**:
1. 发送失败时的提示语
2. 重试机制（间隔、次数限制）

**状态**: 待确认
```

### Phase 3: 异常场景补充

**异常猎手**执行：

#### 步骤 3.1: 异常场景扫描

对每个功能点，使用异常场景检查清单（详见 `references/exception-checklist.md`）：

```yaml
输入异常:
  - 空输入/null
  - 超长输入
  - 特殊字符（<>&"'等）
  - 格式错误
  - 类型错误
  - SQL 注入字符
  - XSS 攻击向量

边界条件:
  - 最小值/最大值
  - 边界±1
  - 空集合/单元素/满集合
  - 零值
  - 负值

状态异常:
  - 网络中断/超时
  - 服务不可用
  - 会话过期
  - 并发冲突
  - 重复提交

数据异常:
  - 数据不存在
  - 数据已删除
  - 数据已修改（乐观锁）
  - 关联数据缺失
  - 数据格式版本不兼容

权限异常:
  - 无权限
  - 权限不足
  - 角色变更
  - Token 过期
```

#### 步骤 3.2: 异常场景记录

**异常场景格式**:

| 编号 | 功能点 | 分类 | 场景 | 触发条件 | 建议处理 | 状态 |
|------|-------|------|------|---------|---------|------|
| E-001 | 手机号验证 | 输入异常 | 非手机号格式 | 输入字母/特殊字符/位数错误 | toast提示 | 待确认 |
| E-002 | 手机号验证 | 状态异常 | 短信服务不可用 | 运营商接口超时 | 重试+备选方案 | 待确认 |

### Phase 4: 交互确认

**交互协调员**执行：

#### 步骤 4.1: 问题分组

将问题按功能模块和严重程度分组，便于逐批确认：

```markdown
分组策略：
1. 按功能模块分组（每组 3-5 个问题）
2. 同一模块内按严重程度排序（致命 > 严重 > 一般 > 轻微）
3. 异常场景单独成组
```

#### 步骤 4.2: 交互式确认

**单个问题确认模板**:
```markdown
---
## 问题 R-001 [严重]

**功能点**: 手机号验证
**问题类型**: 遗漏
**位置**: 2.1.2 注册流程

**原始需求**:
> 系统向用户手机发送验证码

**问题描述**:
未说明验证码发送失败的处理方式

**建议**:
1. 发送失败时的提示语
2. 重试机制（间隔、次数限制）
3. 失败原因分类处理

---
请确认处理方式：
1. **接受建议** - 按建议补充需求
2. **自定义** - 提供您的处理方案
3. **暂不处理** - 记录但不修改
4. **非问题** - 原需求已足够清晰
```

**批量确认模板**:
```markdown
## 模块：用户注册 (共 5 个问题)

| 编号 | 类型 | 严重度 | 问题摘要 | 建议 |
|------|------|--------|---------|------|
| R-001 | 遗漏 | 严重 | 验证码发送失败处理 | 补充重试和提示 |
| R-002 | 歧义 | 一般 | 验证码有效期不明确 | 明确为5分钟 |
| R-003 | 遗漏 | 一般 | 验证码错误次数限制 | 建议5次/小时 |
| R-004 | 遗漏 | 轻微 | 手机号格式校验规则 | 补充正则规则 |
| R-005 | 歧义 | 轻微 | "注册成功"跳转页面 | 明确跳转目标 |

请逐个确认或批量回复：
- 全部接受建议：回复「全部接受」
- 逐个确认：回复问题编号 + 决策（如：R-001 接受，R-002 改为3分钟）
- 跳过此模块：回复「跳过」
```

#### 步骤 4.3: 记录决策

更新问题状态和决策：

| 编号 | 状态 | 用户回复 | 最终决策 |
|------|------|---------|---------|
| R-001 | 已确认 | 接受建议 | 补充：提示「短信发送失败」+ 60秒重试 |
| R-002 | 已确认 | 改为3分钟 | 验证码有效期为3分钟 |

## 分析深度选项

用户可选择分析深度：

| 深度 | 检查范围 | 预计时间 | 适用场景 |
|------|---------|---------|---------|
| **基础** | 五类缺陷扫描 | 5-10分钟 | 快速评审、小需求 |
| **标准** | 缺陷扫描 + 核心异常场景 | 15-30分钟 | 常规需求评审 |
| **深度** | 全面扫描 + 完整异常场景 + 交叉验证 | 30-60分钟 | 重要功能、核心流程 |

## 质量保障

**输入验证**:
- 需求文档非空
- 文档格式可解析
- 内容长度 > 100 字符

**输出验证**:
- 每个功能点至少检查 5 类缺陷
- 每个功能点至少识别 3 个异常场景
- 问题清单格式符合 Schema
- 所有问题有明确状态

**交互规范**:
- 单次确认问题数 ≤ 10 个
- 提供批量确认选项
- 支持跳过和暂存
