# Requirement Tester - 需求测试与规范化

解析原始需求文档，深度分析问题点，与用户交互确认，输出完整规范化的需求文档。

## 设计理念

```
原始需求 → 深度解析 → 问题清单 → 用户确认 → 规范化需求文档 (prd.md)
           (ultra think)   (无废话)    (交互式)    (细致完整)
```

**核心定位**：
- **输入**：任意格式的原始需求（MD/PDF/截图/URL/文本）
- **过程**：深度分析 → 问题清单 → 交互确认
- **输出**：规范化需求文档（prd.md），可直接用于测试用例生成

**与 test-case-generator 的关系**：
```
requirement-tester → prd.md → test-case-generator → cases.jsonl
```

## 适用场景

当用户提供原始需求文档并需要：
- 系统性识别需求中的问题（遗漏、歧义、矛盾等）
- 补充缺失的异常场景和业务规则
- 与产品/业务方交互确认需求细节
- 输出可用于测试用例生成的规范化文档

## 输入方式

支持多种输入格式：

| 格式 | 处理方式 | 状态 |
|------|---------|------|
| Markdown (.md) | Read 工具直接读取 | ✅ 支持 |
| 文本 | 用户直接粘贴 | ✅ 支持 |
| URL | WebFetch/mcp__fetch__fetch | ✅ 支持 |
| PDF (.pdf) | [待实现] PDF 解析工具 | 🔜 待补充 |
| 截图/图片 | [待实现] OCR + 视觉理解 | 🔜 待补充 |
| Word (.docx) | [待实现] 文档解析工具 | 🔜 待补充 |

## 输出结构

```
{需求名称}/
├── issues.md      # 需求问题清单（Phase 1 输出）
└── prd.md         # 规范化需求文档（最终输出）
```

## 工作流程

### Phase 0: 输入获取与解析

**目标**：将任意格式的输入转换为可分析的文本

```yaml
处理流程:
  1. 识别输入类型（文件路径/URL/粘贴文本）
  2. 获取原始内容：
     - MD/TXT: Read 工具
     - URL: WebFetch
     - PDF/截图: [待实现]
  3. 提取核心需求文本
```

**初始信息收集**：

```markdown
请提供需求文档：
1. 文件路径（如：/path/to/prd.md）
2. URL 地址
3. 直接粘贴需求内容

可选信息：
- 需求名称（用于创建输出目录）
- 已知的业务背景/约束
```

---

### Phase 1: 深度解析与问题识别

**目标**：使用 extended thinking 深度分析需求，输出精准的问题清单

#### Step 1.1: 需求结构解析

将原始需求解析为结构化信息：

```yaml
解析维度:
  功能模块:
    - 识别所有功能模块
    - 提取每个模块的核心功能点
    - 识别模块间依赖关系

  业务规则:
    - 数据校验规则
    - 状态流转规则
    - 权限控制规则
    - 计算/逻辑规则

  数据实体:
    - 核心数据对象
    - 字段定义
    - 数据关系
```

#### Step 1.2: 问题扫描（五维度）

对每个功能点执行五维度扫描：

```yaml
遗漏 (Omission):
  - 功能描述是否完整？
  - 异常处理是否定义？
  - 边界条件是否说明？
  - 性能/安全要求是否明确？

歧义 (Ambiguity):
  - 是否有模糊词汇？（快速、大量、适当）
  - 条件判断是否明确？
  - 数值范围是否清晰？

不一致 (Inconsistency):
  - 同一术语定义是否一致？
  - 同一数据在不同场景是否一致？

不完整 (Incompleteness):
  - 流程是否有断点？
  - 状态是否有遗漏？
  - 输入/输出是否完整？

不正确 (Incorrect):
  - 业务规则是否正确？
  - 技术约束是否可行？
```

#### Step 1.3: 异常场景补充

识别需求中未覆盖的异常场景：

```yaml
输入异常:
  - 空值/null
  - 格式错误
  - 超长/超限
  - 特殊字符

边界条件:
  - 最小值/最大值
  - 边界±1
  - 空集合/满集合

状态异常:
  - 网络中断/超时
  - 会话过期
  - 并发冲突
  - 重复操作

权限异常:
  - 无权限访问
  - Token 过期
  - 角色变更
```

#### Step 1.4: 输出问题清单

生成 `issues.md`，格式简洁直接：

```markdown
# 需求问题清单

> 文档：{来源}
> 分析时间：{时间}
> 问题总数：{N} 个

---

## 模块：{模块名称}

### Q1. [严重] {问题标题}

**位置**：{原文位置/引用}

**问题**：{具体问题描述}

**建议**：
1. {建议方案1}
2. {建议方案2}

---

### Q2. [一般] {问题标题}

...

---

## 补充：异常场景

以下异常场景在原需求中未说明处理方式：

| 模块 | 场景 | 触发条件 | 建议处理 |
|------|------|---------|---------|
| 用户登录 | 密码错误 | 连续错误5次 | 锁定30分钟 |
| ... | ... | ... | ... |

---

**请逐一确认上述问题，回复格式：**
- Q1: 接受 / 自定义方案 / 暂不处理
- Q2: ...
```

**问题清单原则**：
- ❌ 无废话、无客套
- ❌ 不重复原文
- ✅ 只有问题和建议
- ✅ 问题编号清晰
- ✅ 支持批量确认

---

### Phase 2: 交互确认（多轮）

**目标**：通过多轮交互，逐步收集用户对所有问题的决策

#### 多轮交互机制

需求确认通常无法一轮完成，支持以下模式：

```yaml
交互流程:
  第一轮:
    - 输出完整问题清单（issues.md）
    - 用户可部分回复，跳过不确定的问题
    - 记录已确认的决策

  后续轮次:
    - 只展示未确认的问题
    - 用户补充之前跳过的问题
    - 可追问：用户的回答引发新问题时继续追问

  结束条件:
    - 所有问题都已确认（状态≠待确认）
    - 或用户明确表示"剩余问题暂不处理"
```

#### 问题状态管理

```yaml
问题状态:
  待确认: 尚未获得用户回复
  已确认: 用户已给出明确答案
  暂不处理: 用户明确跳过
  追问中: 用户回答后产生了新问题
```

#### 交互示例

**首轮 - 输出问题清单**：
```markdown
# 需求问题清单（共 12 个）

## 模块：用户注册 (5个)
Q1. [严重] 验证码发送失败处理
Q2. [一般] 验证码有效期
Q3. [一般] 密码错误次数限制
...

## 模块：用户登录 (4个)
Q6. [严重] 登录失败锁定策略
...

---
请回复确认（可部分回复）：
- Q1: 接受 / 你的方案 / 跳过
- Q2: ...
```

**用户部分回复**：
```
Q1 接受
Q2 改为3分钟
Q6 需要和业务确认，先跳过
```

**后续轮次 - 只展示未确认问题**：
```markdown
# 待确认问题（剩余 9 个）

已确认：Q1, Q2（共 2 个）
暂跳过：Q6（共 1 个）

## 未确认问题：

Q3. [一般] 密码错误次数限制
**问题**：未说明密码连续错误的处理方式
**建议**：5次错误后锁定30分钟

Q4. ...
```

**追问场景**：
```markdown
收到 Q3 的回答：「3次错误后锁定」

追问 Q3-1：锁定时长是多久？
追问 Q3-2：锁定期间是否可以通过其他方式解锁（如验证码）？
```

#### 记录格式

```yaml
确认记录:
  Q1:
    状态: 已确认
    轮次: 1
    用户回复: 接受建议
    最终方案: 验证码发送失败时提示"发送失败"+60秒重试

  Q2:
    状态: 已确认
    轮次: 1
    用户回复: 改为3分钟
    最终方案: 验证码有效期3分钟

  Q3:
    状态: 已确认
    轮次: 2
    用户回复: 3次错误锁定10分钟
    追问:
      - Q3-1: 锁定时长 → 10分钟
      - Q3-2: 支持短信验证码解锁
    最终方案: 密码错误3次锁定10分钟，可通过短信验证码解锁

  Q6:
    状态: 暂不处理
    轮次: 1
    用户回复: 需要和业务确认，先跳过
```

### Phase 3: 规范化需求文档生成

**目标**：整合原始需求和用户确认的补充内容，生成完整规范化的 prd.md

#### 质量标准（核心）

好的需求文档不在于固定结构，而在于满足以下标准：

```yaml
必达标准:
  描述清晰:
    - 无模糊词汇（"快速"→具体秒数，"大量"→具体数量）
    - 条件判断明确（包含/不包含边界值）
    - 术语使用一致

  无待确认问题:
    - 所有 Phase 2 提出的问题都已有明确答案
    - 不存在"待定"、"TBD"、"后续确认"等标记

  无歧义:
    - 同一功能只有一种理解方式
    - 业务规则的触发条件和处理方式都明确
    - 数值范围边界清晰

  交互细节到位:
    - 用户操作有明确响应（成功/失败提示）
    - 异常场景有处理方案
    - 状态变化有说明
```

#### 文档组织建议

保留原始需求的结构，在此基础上：

1. **补充缺失内容**：将用户确认的答案整合到对应位置
2. **消除歧义**：用具体数值替换模糊表述
3. **完善异常处理**：补充遗漏的异常场景
4. **保持可读性**：逻辑清晰，易于理解

#### 可测试性检查

生成的 prd.md 应满足测试用例生成的需要：

- [ ] 每个功能点可独立测试
- [ ] 预期结果可验证（有具体的成功/失败标准）
- [ ] 异常场景可构造（知道如何触发）
- [ ] 边界条件明确（知道边界值是什么）
