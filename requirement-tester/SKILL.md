# 需求测试 Skill

对需求文档进行系统性质量分析，识别缺陷、遗漏和风险，输出规范化需求文档。

## 适用场景

- 新需求文档评审
- PRD/原型评审前的预检
- 需求交付前的质量门禁
- 识别需求中的测试盲点

## 核心分析维度

| 维度 | 关注点 | 典型缺陷 |
|-----|--------|---------|
| 完整性 | 功能覆盖、边界条件、异常流程 | 遗漏场景、缺少约束条件 |
| 一致性 | 需求间逻辑、与上下文系统 | 相互矛盾、版本冲突 |
| 可测性 | 验收标准、量化指标 | 模糊描述、无法验证 |
| 可行性 | 技术实现、资源限制 | 超出能力、依赖不明 |
| 明确性 | 无歧义表述、术语定义 | 多义词、隐含假设 |
| 必要性 | 业务价值、优先级 | 过度设计、重复功能 |
| 界面规范 | 交互逻辑、状态转换 | 状态遗漏、操作歧义 |
| 异常容错 | 错误处理、降级策略 | 异常未定义、无恢复机制 |

## 分析工作流

```
Phase 1: 需求解析
  ├─ 识别文档类型（PRD/原型/截图/口头描述）
  ├─ 提取功能列表和业务规则
  └─ 构建需求结构化表示

Phase 2: 多维度分析
  ├─ 逐条检查 8 个核心维度
  ├─ 记录所有发现的问题
  └─ 标注问题严重程度（阻塞/严重/一般/建议）

Phase 3: 交互确认
  ├─ 向用户展示发现的问题
  ├─ 收集用户反馈和补充信息
  └─ 确认需求理解是否正确

Phase 4: 输出规范化文档
  ├─ 按标准格式重写需求
  ├─ 补充缺失的验收标准
  └─ 生成 prd.md 作为后续用例生成输入
```

## 需求结构化表示格式

为便于 AI 解析且不遗漏，需求应转换为以下结构：

```yaml
requirement:
  id: REQ-001
  name: 用户登录
  type: functional  # functional | non-functional | constraint
  priority: high    # high | medium | low

  description: |
    用户通过手机号和验证码登录系统

  preconditions:
    - 用户已注册
    - 网络连接正常

  actors:
    - 注册用户

  main_flow:
    - step: 1
      action: 用户输入手机号
      expected: 系统校验格式正确性
    - step: 2
      action: 用户点击获取验证码
      expected: 系统发送验证码短信

  alternative_flows:
    - name: 验证码过期
      trigger: 验证码超过5分钟
      steps:
        - 提示验证码已过期
        - 允许重新获取

  exception_flows:
    - name: 手机号格式错误
      trigger: 输入非11位数字
      handling: 前端即时提示格式错误

  acceptance_criteria:
    - 验证码 60 秒内送达
    - 登录响应时间 < 2s
    - 连续错误 5 次锁定账户

  dependencies:
    - 短信服务可用
    - 用户数据库可访问

  open_questions:
    - 验证码有效期多长？
    - 是否支持语音验证码？
```

## 问题分类与严重程度

| 严重程度 | 定义 | 处理要求 |
|---------|------|---------|
| 阻塞 | 无法理解需求意图，无法继续开发 | 必须立即澄清 |
| 严重 | 可能导致重大功能缺陷或安全风险 | 必须在开发前解决 |
| 一般 | 影响用户体验或边界场景 | 应在开发前确认 |
| 建议 | 可优化的设计或描述 | 可选处理 |

## 输出格式

分析报告包含：

1. **需求概览** - 功能点数量、涉及模块
2. **问题清单** - 按严重程度分类的问题列表
3. **补充问题** - 需要用户确认的问题
4. **规范化需求** - 重写后的标准格式需求（prd.md）

## 使用示例

```
用户：帮我分析这个需求文档 [附件]

AI 分析流程：
1. 解析文档，提取功能点
2. 对每个功能点进行 8 维度检查
3. 汇总问题清单
4. 向用户确认关键问题
5. 输出规范化的 prd.md
```
