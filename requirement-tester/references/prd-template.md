# 规范化需求文档 - 质量标准

本文件定义 prd.md 的**质量标准**，而非固定结构。

## 核心标准

好的需求文档满足以下条件即可，不限定具体格式：

### 1. 描述清晰

```yaml
检查项:
  - 无模糊词汇:
      ❌ "快速响应" → ✅ "响应时间 < 500ms"
      ❌ "大量数据" → ✅ "支持 10 万条记录"
      ❌ "适当提示" → ✅ "toast 提示 3 秒后消失"

  - 数值边界明确:
      ❌ "18-60岁" → ✅ "年龄 ≥ 18 且 ≤ 60"
      ❌ "不超过100" → ✅ "≤ 100（包含100）"

  - 术语一致:
      ❌ 同一概念：登录/登陆/签到
      ✅ 全文统一使用"登录"
```

### 2. 无待确认问题

```yaml
检查项:
  - 不存在以下标记:
      - "待定"
      - "TBD"
      - "后续确认"
      - "需要讨论"
      - "?"

  - Phase 2 识别的所有问题都有明确答案
```

### 3. 无歧义

```yaml
检查项:
  - 同一功能只有一种理解方式
  - 条件判断明确（AND/OR、包含/不包含）
  - 优先级冲突时有明确规则
```

### 4. 交互细节到位

```yaml
检查项:
  - 用户操作有响应:
      - 成功时的反馈（toast/跳转/刷新）
      - 失败时的提示（错误信息、引导）

  - 异常场景有处理:
      - 输入错误如何提示
      - 网络异常如何处理
      - 权限不足如何引导

  - 状态变化有说明:
      - 从 A 状态到 B 状态的条件
      - 状态变化后的界面变化
```

---

## 可测试性要求

生成的文档应支持测试用例设计：

| 要求 | 说明 |
|-----|------|
| 功能可验证 | 每个功能有明确的成功/失败标准 |
| 边界可构造 | 知道边界值是什么，能构造测试数据 |
| 异常可触发 | 知道异常条件，能模拟异常场景 |
| 预期可判断 | 预期结果具体，能判断实际结果是否符合 |

---

## 文档组织建议

不强制结构，但建议包含：

- **功能说明**：做什么
- **业务规则**：怎么做（条件、约束）
- **异常处理**：出错时怎么办

具体组织方式可按原始需求文档的结构，在其基础上补充和完善。
