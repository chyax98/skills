# 需求缺陷分类体系

基于 IEEE 830、INCOSE 和学术文献整合的需求缺陷完整分类。

## 一、需求质量属性（IEEE 830 标准）

| 属性 | 英文 | 定义 | 违反时的缺陷 |
|-----|------|------|------------|
| 正确性 | Correct | 需求准确反映用户真实意图 | 描述与实际需要不符 |
| 无歧义 | Unambiguous | 只能有一种理解方式 | 多义词、可多种解读 |
| 完整性 | Complete | 涵盖所有必要信息 | 遗漏场景、缺少约束 |
| 一致性 | Consistent | 需求间无矛盾 | 逻辑冲突、版本不一 |
| 可排序 | Ranked | 有明确优先级 | 无法确定实现顺序 |
| 可验证 | Verifiable | 可通过测试确认实现 | 无法设计测试用例 |
| 可修改 | Modifiable | 易于变更和维护 | 耦合过紧、冗余描述 |
| 可追溯 | Traceable | 可追溯来源和影响 | 来源不明、无法关联 |

## 二、需求缺陷类型详解

### 2.1 缺失/不完整（Missing/Incomplete）

**定义**：需求遗漏了必要的信息或场景

**检查点**：
- 正常流程是否完整描述
- 异常流程是否覆盖
- 边界条件是否定义
- 前置/后置条件是否明确
- 输入输出是否完整
- 性能指标是否量化
- 安全要求是否涵盖

**示例**：
```
缺陷：用户可以上传图片
问题：未说明支持的格式、大小限制、数量限制

修正：用户可以上传图片
      - 格式：JPG/PNG/GIF
      - 单张大小：≤5MB
      - 单次最多：9张
```

### 2.2 错误/不正确（Incorrect）

**定义**：需求描述与实际业务逻辑或技术约束不符

**检查点**：
- 业务规则是否正确
- 计算公式是否准确
- 引用数据是否真实
- 技术假设是否成立

**示例**：
```
缺陷：订单金额 = 商品单价 × 数量
问题：未考虑优惠券、满减、积分抵扣

修正：订单金额 = (商品单价 × 数量) - 优惠券 - 满减金额 - 积分抵扣
```

### 2.3 不一致（Inconsistent）

**定义**：需求之间存在逻辑矛盾或冲突

**检查点**：
- 同一概念是否定义一致
- 数值范围是否冲突
- 流程分支是否矛盾
- 与现有系统是否兼容

**示例**：
```
缺陷：
  需求A：用户密码长度 6-12 位
  需求B：密码必须包含大小写字母和数字，至少 8 位
问题：长度要求冲突

修正：用户密码长度 8-12 位，必须包含大小写字母和数字
```

### 2.4 模糊/歧义（Ambiguous/Unclear）

**定义**：需求可以有多种理解方式

**高频歧义词汇**：

| 歧义词 | 问题 | 如何修正 |
|-------|------|---------|
| 快速 | 多快？ | 响应时间 < 2s |
| 大量 | 多少？ | 支持 10000 条/页 |
| 灵活 | 怎么灵活？ | 支持拖拽排序 |
| 友好 | 什么算友好？ | 提供操作引导和帮助文档 |
| 容易 | 怎么算容易？ | 3 步内完成操作 |
| 适当 | 什么范围？ | 5-10 个选项 |
| 如有必要 | 谁决定？何时？ | 当 X 条件满足时 |
| 等 | 还有什么？ | 明确列出完整清单 |

**示例**：
```
缺陷：系统应快速响应用户请求
问题："快速"没有量化标准

修正：系统响应用户请求的时间 ≤ 200ms（P99）
```

### 2.5 不可行（Infeasible）

**定义**：技术上无法实现或资源不支持

**检查点**：
- 技术栈是否支持
- 第三方服务是否可用
- 性能指标是否可达
- 时间/成本是否合理
- 法规/合规是否允许

**示例**：
```
缺陷：支持所有浏览器
问题：IE6 等老旧浏览器技术栈不支持

修正：支持 Chrome 80+、Firefox 75+、Safari 13+、Edge 80+
```

### 2.6 不可验证（Non-Verifiable）

**定义**：无法通过测试确认是否实现

**不可验证的特征**：
- 使用主观形容词（美观、易用）
- 无量化指标
- 条件不明确
- 无法重现的场景

**示例**：
```
缺陷：界面应该美观大方
问题：无法客观测试

修正：
  - 遵循 Material Design 规范
  - 主色调使用 #1890FF
  - 通过 UI 评审验收
```

### 2.7 冗余（Redundant）

**定义**：信息重复描述或不必要

**检查点**：
- 是否与其他需求重复
- 是否过度解释
- 是否包含实现细节

### 2.8 过度规范（Over-specification）

**定义**：限制了不必要的实现方式

**示例**：
```
缺陷：使用 MySQL 5.7 存储用户数据，表结构为...
问题：过度规定技术实现

修正：持久化存储用户数据，支持 CRUD 操作，数据保留 3 年
```

### 2.9 放错位置（Misplaced）

**定义**：需求放在了错误的章节或文档

**检查点**：
- 功能需求和非功能需求是否混淆
- 系统需求和用户需求是否区分
- 约束和需求是否分开

## 三、INCOSE 需求质量特性

| 特性 | 定义 | 检查问题 |
|-----|------|---------|
| 必要性 (Necessary) | 需求对业务有价值 | 删除会影响系统功能吗？ |
| 适当性 (Appropriate) | 描述 what 而非 how | 是否限制了实现方式？ |
| 无歧义 (Unambiguous) | 只有一种理解 | 不同人读是否有不同理解？ |
| 完整性 (Complete) | 信息充分 | 能否据此设计和测试？ |
| 单一性 (Singular) | 一条需求一件事 | 是否包含多个独立需求？ |
| 可行性 (Feasible) | 技术可实现 | 现有技术能否支持？ |
| 可验证 (Verifiable) | 可测试 | 能否设计验收标准？ |
| 正确性 (Correct) | 准确无误 | 是否符合业务事实？ |
| 符合规范 (Conforming) | 格式统一 | 是否遵循文档规范？ |
| 一致性 (Consistent) | 无矛盾 | 与其他需求是否冲突？ |

## 四、基于视角的需求检查（PBR）

不同角色关注的缺陷类型不同：

### 4.1 开发者视角

- 技术可行性
- 性能约束是否合理
- 接口定义是否清晰
- 依赖关系是否明确

### 4.2 测试者视角

- 验收标准是否可测
- 边界条件是否明确
- 异常场景是否覆盖
- 测试数据需求

### 4.3 用户视角

- 操作流程是否合理
- 业务场景是否完整
- 用语是否易懂
- 是否符合使用习惯

### 4.4 运维视角

- 监控需求是否明确
- 日志规范是否定义
- 容灾要求是否清晰
- 配置管理需求

## 五、缺陷统计与优先级

根据行业数据，需求缺陷分布大致为：

| 缺陷类型 | 占比 | 影响 |
|---------|-----|------|
| 不完整 | 30-40% | 功能遗漏 |
| 模糊歧义 | 25-35% | 理解偏差 |
| 不一致 | 10-15% | 逻辑冲突 |
| 不可验证 | 10-15% | 无法测试 |
| 错误 | 5-10% | 功能错误 |
| 其他 | 5-10% | 各类问题 |

处理优先级：**正确性 > 完整性 > 一致性 > 明确性 > 可验证性 > 其他**
