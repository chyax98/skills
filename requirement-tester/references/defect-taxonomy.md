# 需求缺陷分类体系

> 基于 IEEE Std 1044-2009 和行业最佳实践

## 缺陷分类概览

```
需求缺陷
├── 遗漏 (Omission)
│   ├── 功能遗漏
│   ├── 场景遗漏
│   ├── 异常遗漏
│   ├── 性能遗漏
│   └── 安全遗漏
│
├── 歧义 (Ambiguity)
│   ├── 术语歧义
│   ├── 逻辑歧义
│   ├── 范围歧义
│   └── 优先级歧义
│
├── 不一致 (Inconsistency)
│   ├── 内部不一致
│   ├── 外部不一致
│   └── 版本不一致
│
├── 不完整 (Incompleteness)
│   ├── 输入不完整
│   ├── 输出不完整
│   ├── 流程不完整
│   └── 约束不完整
│
└── 不正确 (Incorrect)
    ├── 事实错误
    ├── 逻辑错误
    └── 不可行
```

## 一、遗漏 (Omission)

**定义**: 缺少必要的需求说明

### 1.1 功能遗漏

**检查点**:
- [ ] 用户可执行的操作是否都有描述？
- [ ] 系统自动触发的行为是否都有说明？
- [ ] 数据的增删改查操作是否完整？
- [ ] 批量操作是否支持？

**常见遗漏**:
```yaml
用户操作:
  - 取消/撤销操作
  - 批量操作
  - 导入/导出功能
  - 搜索/筛选功能
  - 排序功能
  - 分页处理

系统行为:
  - 定时任务
  - 触发条件
  - 通知机制
  - 日志记录
  - 数据同步
```

**提问模板**:
- "用户能否取消这个操作？如何取消？"
- "支持批量处理吗？一次最多处理多少？"
- "操作完成后系统会发送通知吗？"

### 1.2 场景遗漏

**检查点**:
- [ ] 首次使用场景是否覆盖？
- [ ] 多角色场景是否覆盖？
- [ ] 多端同步场景是否覆盖？
- [ ] 离线/弱网场景是否覆盖？

**常见遗漏**:
```yaml
用户场景:
  - 新用户引导
  - 老用户迁移
  - 游客访问
  - 多角色切换

设备场景:
  - 多端登录
  - 设备切换
  - 屏幕适配

网络场景:
  - 离线模式
  - 弱网环境
  - 网络切换
```

### 1.3 异常遗漏

**检查点**:
- [ ] 输入错误如何处理？
- [ ] 操作失败如何提示？
- [ ] 网络异常如何处理？
- [ ] 服务不可用如何降级？

**常见遗漏**:
```yaml
输入异常:
  - 空输入
  - 格式错误
  - 超长输入
  - 非法字符

操作异常:
  - 重复提交
  - 并发冲突
  - 超时处理
  - 权限不足

系统异常:
  - 服务降级
  - 数据回滚
  - 错误恢复
```

### 1.4 性能遗漏

**检查点**:
- [ ] 响应时间要求是否明确？
- [ ] 并发用户数是否定义？
- [ ] 数据量级是否说明？
- [ ] 资源限制是否说明？

**关键指标**:
```yaml
响应时间:
  - 页面加载: < X 秒
  - 接口响应: < X 毫秒
  - 批量操作: < X 秒/每百条

并发能力:
  - 同时在线: X 用户
  - 峰值 QPS: X
  - 数据库连接: X

数据量级:
  - 单表数据: X 万条
  - 单次查询: X 条
  - 文件大小: X MB
```

### 1.5 安全遗漏

**检查点**:
- [ ] 认证方式是否说明？
- [ ] 权限控制是否定义？
- [ ] 敏感数据是否保护？
- [ ] 审计日志是否要求？

**安全要求**:
```yaml
认证:
  - 登录方式
  - 会话管理
  - 密码策略

授权:
  - 角色定义
  - 权限矩阵
  - 数据隔离

数据保护:
  - 加密传输
  - 加密存储
  - 脱敏展示

审计:
  - 操作日志
  - 登录日志
  - 异常告警
```

## 二、歧义 (Ambiguity)

**定义**: 需求可有多种理解

### 2.1 术语歧义

**危险词汇列表**:
```yaml
模糊数量词:
  - "大量" → 具体数值是多少？
  - "少量" → 具体阈值是多少？
  - "多个" → 最少几个？最多几个？
  - "部分" → 哪些部分？比例？

模糊程度词:
  - "快速" → 具体多少秒/毫秒？
  - "高效" → 用什么指标衡量？
  - "友好" → 有哪些具体要求？
  - "简洁" → 具体展示哪些字段？

模糊频率词:
  - "经常" → 具体频率？
  - "定期" → 多长周期？
  - "实时" → 延迟容忍度？
  - "及时" → 多长时间内？

模糊条件词:
  - "适当" → 具体条件是什么？
  - "必要时" → 什么情况下？
  - "可能" → 概率？条件？
  - "一般情况" → 例外情况有哪些？
```

**提问模板**:
- "「大量数据」具体指多少条记录？"
- "「快速响应」的具体时间要求是多少秒？"
- "「定期」是指每天、每周还是每月？"

### 2.2 逻辑歧义

**检查点**:
- [ ] AND/OR 条件是否明确？
- [ ] 条件优先级是否清晰？
- [ ] 边界判断（>= vs >）是否明确？

**示例**:
```markdown
歧义表述:
"当用户余额不足或会员过期时，禁止购买"

需要澄清:
1. 余额不足的阈值是 0 还是商品价格？
2. 两个条件是 AND 还是 OR 关系？
3. "禁止"是指按钮置灰还是弹窗提示？
```

### 2.3 范围歧义

**检查点**:
- [ ] 数值范围是否包含边界？
- [ ] 时间范围是否包含端点？
- [ ] 列表是否穷尽？

**示例**:
```markdown
歧义表述:
"年龄在 18-60 岁之间的用户可以注册"

需要澄清:
1. 18 岁和 60 岁是否包含？（>= 18 AND <= 60）
2. 年龄按周岁还是虚岁计算？
3. 以什么时间点计算年龄？
```

### 2.4 优先级歧义

**检查点**:
- [ ] 多个条件冲突时如何处理？
- [ ] 多个规则适用时哪个优先？
- [ ] 多个状态同时存在时显示哪个？

## 三、不一致 (Inconsistency)

**定义**: 需求之间相互矛盾

### 3.1 内部不一致

**检查点**:
- [ ] 同一术语在不同章节定义是否一致？
- [ ] 同一字段在不同页面展示是否一致？
- [ ] 同一操作在不同入口行为是否一致？

**常见不一致**:
```yaml
术语不一致:
  - 登录/登陆
  - 用户/会员/客户
  - 订单/工单
  - 审核/审批

数据不一致:
  - 字段名称不同
  - 格式要求不同
  - 精度要求不同
  - 默认值不同

行为不一致:
  - 相同操作不同入口表现不同
  - 相同条件不同页面结果不同
```

### 3.2 外部不一致

**检查点**:
- [ ] 与现有系统功能是否冲突？
- [ ] 与第三方接口规范是否一致？
- [ ] 与行业标准是否符合？

### 3.3 版本不一致

**检查点**:
- [ ] 需求更新后，关联需求是否同步更新？
- [ ] 原型、文档、接口文档是否版本一致？

## 四、不完整 (Incompleteness)

**定义**: 需求描述不够详尽

### 4.1 输入不完整

**检查清单**:
```yaml
数据输入:
  - [ ] 所有输入字段是否列出？
  - [ ] 每个字段的格式要求？
  - [ ] 每个字段的长度限制？
  - [ ] 必填/选填是否标注？
  - [ ] 默认值是否定义？

文件输入:
  - [ ] 支持的文件格式？
  - [ ] 文件大小限制？
  - [ ] 文件内容校验规则？
```

### 4.2 输出不完整

**检查清单**:
```yaml
页面输出:
  - [ ] 展示字段是否完整？
  - [ ] 字段展示顺序？
  - [ ] 空数据如何展示？
  - [ ] 超长数据如何处理？

接口输出:
  - [ ] 响应字段是否完整？
  - [ ] 错误码是否定义？
  - [ ] 分页规则是否说明？
```

### 4.3 流程不完整

**检查清单**:
```yaml
业务流程:
  - [ ] 开始条件是否明确？
  - [ ] 结束条件是否明确？
  - [ ] 中间步骤是否完整？
  - [ ] 分支条件是否覆盖？
  - [ ] 回退机制是否说明？

状态流转:
  - [ ] 所有状态是否列出？
  - [ ] 状态间流转条件？
  - [ ] 是否存在终态？
  - [ ] 异常状态如何处理？
```

### 4.4 约束不完整

**检查清单**:
```yaml
业务约束:
  - [ ] 时间限制（有效期、超时）？
  - [ ] 次数限制（重试、操作频率）？
  - [ ] 数量限制（单次、总量）？
  - [ ] 金额限制（单笔、累计）？

技术约束:
  - [ ] 浏览器兼容性？
  - [ ] 设备兼容性？
  - [ ] 版本兼容性？
```

## 五、不正确 (Incorrect)

**定义**: 需求与真实业务不符

### 5.1 事实错误

**检查点**:
- [ ] 业务规则是否与实际流程一致？
- [ ] 计算公式是否正确？
- [ ] 引用的标准是否最新有效？

### 5.2 逻辑错误

**检查点**:
- [ ] 条件判断是否有遗漏？
- [ ] 边界条件是否正确处理？
- [ ] 循环/递归是否有终止条件？

### 5.3 不可行

**检查点**:
- [ ] 技术上是否可实现？
- [ ] 性能要求是否可达到？
- [ ] 时间/资源是否足够？

## 严重程度定义

| 级别 | 定义 | 影响 | 处理优先级 |
|------|------|------|-----------|
| **致命** | 导致系统无法使用或数据丢失 | 核心功能不可用 | 必须在开发前修复 |
| **严重** | 核心功能受损或重要流程中断 | 用户无法完成关键任务 | 应在开发前修复 |
| **一般** | 功能可用但体验不佳 | 用户可绕过使用 | 建议在开发前修复 |
| **轻微** | 不影响使用的小问题 | 用户几乎无感知 | 可在后续迭代修复 |

## 使用指南

### 扫描顺序

建议按以下顺序扫描：
1. **遗漏** - 最常见，影响最大
2. **歧义** - 常见，容易被忽视
3. **不一致** - 需要跨章节对比
4. **不完整** - 需要详细检查每个字段
5. **不正确** - 需要业务知识验证

### 提问技巧

**开放式提问**:
- "如果...会发生什么？"
- "用户还可能怎么操作？"
- "这种情况下系统如何响应？"

**封闭式确认**:
- "这里的「大量」是指超过 1000 条吗？"
- "边界值 100 是包含还是不包含？"
- "两个条件是 AND 关系还是 OR 关系？"
